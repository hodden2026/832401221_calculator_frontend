# Frontend Code Style Guide

## 1. Code Style References

The frontend coding conventions of this project are mainly based on the following widely recognized standards and recommendations:

- Google JavaScript Style Guide
- MDN Web Docs — HTML
- MDN Web Docs — CSS
- MDN Web Docs — JavaScript

The project follows these standards while making reasonable adjustments according to the scale and requirements of the calculator system.

---

## 2. General Principles

The frontend code should remain:

- Readable
- Consistent
- Modular
- Easy to maintain
- Clearly separated from backend responsibilities

The frontend is responsible for user interaction and information display.

The frontend must not perform the final mathematical calculation.

The final calculation result must always be generated by the backend.

---

## 3. HTML Coding Conventions

### 3.1 Semantic HTML

Use semantic HTML elements whenever possible.

Recommended elements include:

```html
<header></header>
<main></main>
<section></section>
<footer></footer>
```

Avoid unnecessary nested elements.

Use `<button>` for clickable buttons instead of clickable `<div>` elements.

---

### 3.2 Indentation

Use 4 spaces for indentation.

Do not use tabs.

Example:

```html
<section class="calculator-card">
    <h2>Calculator</h2>

    <button type="button">
        Calculate
    </button>
</section>
```

---

### 3.3 Element and Attribute Naming

HTML element names and attribute names should use lowercase letters.

Example:

```html
<button type="button">
    Calculate
</button>
```

---

### 3.4 Class and ID Naming

Use kebab-case for CSS classes and HTML IDs.

Correct examples:

```html
<div id="history-list"></div>

<div class="calculator-card"></div>

<button class="delete-history-button">
    Delete
</button>
```

Avoid names such as:

```text
historyList
CalculatorCard
delete_history_button
```

---

### 3.5 Accessibility

Interactive elements should use appropriate HTML elements.

Buttons should use:

```html
<button></button>
```

Important error messages should provide appropriate semantic information.

Example:

```html
<div
    id="error-message"
    role="alert"
></div>
```

---

### 3.6 Page Structure

The main page structure should be clear and organized.

The calculator page is divided into:

- Page header
- Calculator section
- Calculation display
- Calculator buttons
- Keyboard shortcut information
- Calculation history section
- History search
- Page footer

---

## 4. CSS Coding Conventions

### 4.1 Class Naming

CSS class names use kebab-case.

Examples:

```css
.calculator-card
.history-item
.history-search
.delete-history-button
.theme-toggle-button
```

---

### 4.2 CSS Variables

Reusable colors and shared style values should use CSS custom properties.

Example:

```css
:root {
    --background: #f3f4f6;
    --card-background: #ffffff;
    --text-primary: #1f2937;
}
```

This makes theme switching and future maintenance easier.

---

### 4.3 Layout

Prefer modern layout technologies.

Recommended:

- CSS Grid
- Flexbox

Example:

```css
.page-container {
    display: grid;
    grid-template-columns: 1fr 1fr;
    gap: 24px;
}
```

Avoid unnecessary absolute positioning.

---

### 4.4 Responsive Design

The page should remain usable on different screen sizes.

Use media queries where necessary.

Example:

```css
@media (max-width: 800px) {
    .page-container {
        grid-template-columns: 1fr;
    }
}
```

---

### 4.5 Reusable Styles

Avoid repeating identical style definitions.

Shared colors, borders, backgrounds, and other commonly used values should be reused whenever possible.

---

### 4.6 Theme Design

The project supports light and dark themes.

Theme-related values should be controlled through CSS variables rather than duplicating the entire stylesheet.

Example:

```css
body.dark-theme {
    --background: #111827;
    --card-background: #1f2937;
    --text-primary: #f9fafb;
}
```

---

### 4.7 CSS Organization

CSS should be organized into logical sections.

For this project, the stylesheet is divided into sections such as:

- Global variables
- Dark theme
- Basic page styles
- Header
- Main layout
- Cards
- Display area
- Calculator buttons
- History
- Search
- Footer
- Responsive design

Section comments may be used to improve readability.

---

## 5. JavaScript Coding Conventions

### 5.1 Variable Naming

Use camelCase for variables.

Examples:

```javascript
expressionDisplay
resultDisplay
historyList
historyCache
```

---

### 5.2 Function Naming

Use camelCase for function names.

Function names should clearly describe their purpose.

Examples:

```javascript
calculateExpression()
loadHistory()
deleteHistory()
clearAllHistory()
filterHistory()
toggleTheme()
checkBackendStatus()
```

Avoid unclear names such as:

```javascript
doThing()
handleStuff()
func1()
```

---

### 5.3 Constants

Configuration constants should use uppercase snake case.

Example:

```javascript
const API_BASE_URL = "http://127.0.0.1:5000";
```

---

### 5.4 `const` and `let`

Use `const` by default when reassignment is not required.

Use `let` only when a variable must be reassigned.

Example:

```javascript
const historyList =
    document.getElementById("history-list");

let expression = "";
```

Do not use:

```javascript
var
```

unless there is a specific reason.

---

### 5.5 Function Responsibilities

Each function should perform one clear task.

Examples:

```javascript
appendValue()
```

is responsible for adding input to the expression.

```javascript
loadHistory()
```

is responsible for retrieving history from the backend.

```javascript
renderHistory()
```

is responsible for displaying history records.

```javascript
deleteHistory()
```

is responsible for sending a delete request to the backend.

Avoid placing all frontend logic inside one very large function.

---

### 5.6 Asynchronous Code

Use `async` and `await` for HTTP requests.

Example:

```javascript
const response = await fetch(
    `${API_BASE_URL}/api/history`
);

const data = await response.json();
```

Network requests should be protected using `try...catch`.

Example:

```javascript
try {
    const response = await fetch(url);
    const data = await response.json();
} catch (error) {
    console.error(error);
}
```

---

### 5.7 DOM Operations

Frequently used DOM elements should be stored in variables.

Example:

```javascript
const resultDisplay =
    document.getElementById("result-display");
```

Avoid repeatedly calling:

```javascript
document.getElementById(...)
```

for the same element.

---

### 5.8 Event Handling

Use `addEventListener()` to register events.

Example:

```javascript
button.addEventListener(
    "click",
    calculateExpression
);
```

Avoid using inline JavaScript such as:

```html
<button onclick="calculate()">
```

---

## 6. Front-End / Back-End Separation Rules

The frontend must only handle:

- User interface presentation
- Calculator button interaction
- Expression input
- Sending HTTP requests
- Displaying calculation results
- Displaying calculation history
- Searching history
- Sending history deletion requests
- Displaying backend error messages
- Theme switching
- Keyboard interaction

The frontend must not perform the final mathematical calculation.

For example, the following design is prohibited:

```text
Frontend calculates result
        ↓
Frontend sends result to backend
        ↓
Backend only stores result
```

The required design is:

```text
User enters expression
        ↓
Frontend sends expression
        ↓
Backend validates expression
        ↓
Backend parses expression
        ↓
Backend calculates result
        ↓
Backend stores history
        ↓
Backend returns result
        ↓
Frontend displays result
```

---

## 7. API Request Rules

The frontend communicates with the backend through HTTP APIs.

Main APIs:

```text
POST   /api/calculate
GET    /api/history
DELETE /api/history/{id}
DELETE /api/history
GET    /api/health
```

Requests that send JSON data must specify:

```javascript
headers: {
    "Content-Type": "application/json"
}
```

Example:

```javascript
body: JSON.stringify({
    expression: expression
})
```

The frontend sends the expression only.

It does not send a calculated final result to the backend.

---

## 8. Error Handling Rules

Network errors must be handled gracefully.

If the backend cannot be reached, the frontend should display a clear message instead of silently failing.

Example:

```text
无法连接后端服务器，请检查后端是否启动
```

Backend error messages such as:

```text
Division by zero
Invalid expression
```

should be displayed to the user.

---

## 9. Security Rules

### 9.1 No Arbitrary Code Execution

The frontend must not execute calculator input as JavaScript code.

Do not use user input with dangerous arbitrary-code execution approaches.

---

### 9.2 Calculation Responsibility

The frontend must not calculate the authoritative final result.

All mathematical calculations must be completed by the backend.

---

### 9.3 History Storage

Calculation history must not rely on:

- Browser memory
- LocalStorage
- SessionStorage
- Temporary frontend arrays

as the authoritative data source.

The calculation history displayed on the page must come from the backend database.

---

### 9.4 LocalStorage Usage

LocalStorage may only be used for non-critical interface preferences.

In this project, LocalStorage is used only to remember the selected light or dark theme.

It is not used to store calculation history.

---

## 10. Keyboard Shortcut Rules

The calculator supports keyboard shortcuts.

Supported keys include:

| Key | Function |
|---|---|
| `0-9` | Number input |
| `+` | Addition |
| `-` | Subtraction |
| `*` | Multiplication |
| `/` | Division |
| `(` `)` | Parentheses |
| `.` | Decimal point |
| `Enter` | Calculate |
| `Backspace` | Delete last character |
| `Escape` | Clear calculator |

Keyboard shortcuts should not interfere with normal typing inside input fields such as the history search box.

---

## 11. History Display Rules

History records must be retrieved from the backend.

Each displayed history item may contain:

- Record ID
- Expression
- Result
- Calculation time
- Delete button

After deleting a record, the frontend should retrieve the latest history from the backend again.

---

## 12. History Search Rules

History search is a frontend display feature.

It may filter the history records already retrieved from the backend.

Search may match:

- Expression
- Result
- Calculation time

Searching must not modify the underlying database.

## 14. Comments

Comments should explain important design decisions or non-obvious logic.

Good example:

```javascript
/*
 * The frontend does not calculate the final result.
 * The expression is sent to the backend API.
 */
```

Avoid unnecessary comments that simply repeat obvious code.

---

## 15. Code Maintenance

When modifying frontend code:

1. Keep frontend and backend responsibilities separated.
2. Avoid duplicating existing functions.
3. Reuse existing CSS variables where possible.
4. Keep naming conventions consistent.
5. Test calculator input after changes.
6. Test API communication after changes.
7. Test history loading and deletion.
8. Test keyboard shortcuts.
9. Test responsive layout.
10. Test both light and dark themes.

---

## 16. Summary

The frontend follows the principles of:

- Clear structure
- Consistent naming
- Semantic HTML
- Modular JavaScript
- Responsive CSS
- Secure frontend/backend separation
- Backend-based calculation
- Backend-based persistent history storage

These conventions are used to keep the project readable, maintainable, and consistent.
